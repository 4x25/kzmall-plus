# 安全与预算边界

本文件解释三条硬规则背后的机制，以及脚本为什么会在某些情况下直接拒绝执行。
遇到"脚本报错但我觉得应该能跑"时先看这里——多数拒绝是刻意的。

## 一、算术必须由脚本完成

### 为什么

大模型对多位小数的连续累加不可靠，而这里的每个数字都会进入用户的经营决策。
更麻烦的是：口算错了不会有任何报错，用户也无法复查。所以本技能把"算什么"和"怎么算"分开——
你负责前者，脚本负责后者，并且脚本输出里带着字段名、行数和完整性校验，任何结论都能被逐步倒查。

### 机制

`kz-fetch.mjs` 只把 manifest 打到 stdout，数据行写入 `--out` 文件。你拿不到原始行，
自然也无法手工累加。计算必须经过 `kz-compute.mjs` 或你写的 Node 脚本。

`kz-money.mjs` 用放大 1e6 的 BigInt 做定点运算：金额是"分"级数据，浮点累加到几千行以后
会产生用户看得见的差额。无法解析的单元格计入 `cells_unparsable` 而不是当成 0——
把"缺数据"和"金额为零"混为一谈是另一类静默错误。

### 唯一例外

接口本身返回的**单个数字**可以直接引用，前提是**指明字段来源**，例如
"昨天销售额 12,345.67（`day-report` 的 `sale_fee`）"。
一旦要把两个数字放到一起做任何运算（求和、求差、算占比、比大小排名、算日均），
就必须落到脚本里。"只是两个数相加"也不例外——例外一旦开口就守不住了。

### `--preview` 的定位

`--preview N`（最多 5 行）只用于确认字段名和取值形态，比如确认某列是 `"1,234.50"` 这种带逗号的字符串。
不得据此估算或手算任何合计。

## 二、Token 不得泄露

### 机制

- Token 只从 `process.env.KZP_AGENT_TOKEN` 读取。`loadConfig()` 会扫描 `process.argv`，
  发现形如 `kza_v1_...` 的参数就直接抛错——因为命令行参数会进入 shell 历史和进程列表，等于泄露。
- 所有错误输出经过 `redact()`：Token 原值和 `kza_v1_[A-Za-z0-9_-]{8,}` 模式都会被替换成
  `kza_v1_<redacted>`。
- `X-Credential` 请求头从不打印。`kz-doctor.mjs` 只报告"已设置、前缀 `kza_v1_`、长度 N"，
  这些特征不足以重建凭证。

### 你要遵守的

不要把 Token 写进：命令行参数、脚本文件、数据文件、日志、报告、对用户的回答、提交的代码。
用户问"我的 token 是什么"时也不要回显——让他们去 kzmall-plus 的"Agent 凭证"页面查看。
自己写的脚本同样只能从环境变量读，并且不要把 `process.env` 整体打印出来。

Token 是永久有效的全权限凭证（撤销或轮换之前一直有效），泄露后果比一次性密码严重得多。

## 三、只调用注册表内的接口

### 机制

`kz-endpoints.mjs` 穷举了所有允许的端点。`getEndpoint()` 在键不存在时抛错并列出可用键，
没有 `--path` 之类的逃生舱口。每个端点的方法、路径、有序查询模板、请求体形态、成功谓词、
行容器路径都是抓包取证的结果，不是推测。

### 为什么不能"推测一个看起来合理的路径"

快准车服的接口有大量反直觉之处：同名参数在不同报表里含义不同、成功谓词逐端点不同、
真实请求带重复的 `action` 键、有的端点要零字节请求体 + urlencoded 头。
一个"看起来合理"的路径要么 404，要么更糟——返回一个不同口径的结果，而你无从判断。

### 注册表只暴露实测生效的参数

有些参数网页会发、后端也接受，但**根本不筛选行**。它们在注册表里被固定成空值，传了会报错并指向 `--describe`。
留着比不留危险：一个不生效的筛选条件会让你以为看的是子集、实际看的是全表，而两边都不会报错。

已证明无效并固定留空的（实测"加与不加响应逐字节相同"）：`sales-detail` / `sales-summary-by-goods` /
`deliver-summary` 的 `storageNo`，`inv-balance` 的 `goodsNo` / `storage`，
`deliver-summary` 的 `goodsNo` / `storage`，`sales-detail` 的 `cateoryTreeValue`（无合法取值来源）。
要按仓库看**销售**就取 `sales-summary-by-goods`，按行里的 `locationNo` 本地分组。

`inv-balance` 的 `storageNo` 是个例外，而且这条曾经记错过：它**确实筛行**。实测全量 8134 行、
`storageNo=KZ001` 得 7965 行、`storageNo=S001` 得 169 行，行数与 `allcost_1` 都逐分构成精确划分。
带上它响应会少一组仓库列（22 → 19），`allcost_1`/`qty_1` 也随之变成该仓库口径而不是全仓合计。
这个更正不只是补个参数——它是下面那节"分片丢行"里唯一能补齐缺口的手段。

反过来，注册表里保留了几个看起来像拼写错误的键（`cateoryTreeValue`、`salepPofitRate`、`delieverId`）——
那是后端的真实线格式，"修正"它们会让参数失效或字段读不到。

### 不在注册表里的几类，以及替代方案

| 想做的事 | 为什么不行 | 怎么办 |
|---|---|---|
| 按商品名搜商品 id | 商品列表响应是依赖页面会话密钥的 `kziv` 加密串，纯 HTTP 拿不到明文 | 让用户提供商品编码，或用分类/品牌筛选后从 `rank` 结果定位 |
| 应收账款总表/明细表 | FineReport 会话化报表协议，不是稳定 REST | 用 `customer-balance` |
| 库存成本明细 | `inv-balance` 的成本变体未纳入 | 用 `day-report` 的 `qc_store_fee`/`store_fee` 说明服务站级库存金额 |
| 导出 Excel | 导出接口不在注册表，且属于"为了补全而导出" | 缩小范围后正常查询 |
| 任何写操作 | 凭证背后是生产账号 | 明确拒绝，说明本技能只读 |

## 四、数据完整性与查询预算

这一节讲的都是同一件事的两面：**怎么知道手里这份数据是完整的，以及为什么不能为了"看起来完整"去加大请求。**
下面几个小节按"会出什么错"排列，而且是越往后越隐蔽——

- [查询预算](#查询预算)：请求多大算过界
- [分页是否闭合](#分页是否闭合)：什么时候才能宣称翻完了
- [完整性交叉核对](#完整性交叉核对)：`integrity` 怎么读，页脚帮不上忙时怎么办
- [后端混在明细里的伪行](#后端混在明细里的伪行)：合计行混进明细会让数字翻倍
- [分组键丢行](#分组键丢行)：排名静默少算，但至少会报警告
- [筛选丢行](#筛选丢行比分组更隐蔽因为它不触发上面那个警告)：连那个警告都不响
- [分片丢行](#分片丢行错在取数阶段所有完整性检查都看不见)：行根本没进文件，页脚也证明不了缺口
- [数据新鲜度是逐端点的](#数据新鲜度是逐端点的)：跨报表对不上不一定是谁算错了
- [无界断言](#无界断言问题问的是从来端点只给得出这段时间)：数据是完整的，但覆盖的时间比问题短

### 查询预算

这些数值是数据最小化策略，不是对后端能力的推断。网页为本地表格加载设置的 `rows=3000`、
`rows=1000000`、`loadonce` 不是 Agent 的默认值。

| 限制 | 数值 | 脚本行为 |
|---|---|---|
| 单次响应字节 | 2 MiB | 超限中止并报 `RESPONSE_TOO_LARGE`，不自动改大页 |
| 有可靠分页的端点单页行数 | ≤ 200 | 超过直接报错；自动按页续取 |
| 日期报表默认跨度 | ≤ 31 天 | 超过报错并建议改用月度端点 |
| 销售明细/汇总、商品收发、现金银行、应付明细 | ≤ 7 天 | 超过报错并建议 `--split` |
| 单次命令请求数 | 默认 12（`--max-requests`） | 超过报错，不静默截断 |

### 分页是否闭合

只有 `page`/`records`/`total` 这类总数或总页路径已确认时，才能宣称完整翻页。
本技能里这三类端点有可靠分页：`sales-order-list`、`sales-return-list`、`receipt-list`、`warehouse-list`。

其余端点虽然接受 `page`/`rows`，但响应没有可靠分页元数据。对它们：

- 只取有界第一页，manifest 里 `pagination_complete: false`
- **不用"短页/空页"经验规则自动续页**——这个经验在 `bank-journal` 上已被证伪（`rows=1` 仍返回多行）
- `bank-journal` 和 `payable-detail` 直接禁止 `--page 2`
- 行数达到本次请求上限时置 `possibly_truncated: true`

`possibly_truncated: true` 时 `kz-compute.mjs` **拒绝计算**（除非显式 `--allow-incomplete`）。
理由很直接：截断数据上的合计是错的，而错的合计比没有答案更有害。

### 完整性交叉核对

多数报表返回服务端算好的页脚（`data.userdata` / `data.total`）。`kz-compute.mjs` 的每次输出都带
`integrity`：把脚本对行的求和与页脚对比。

- `all_match: true` —— 取到的行覆盖了该字段的完整口径，结论可用
- `all_match: false` —— 存在截断或口径差异，**先解释再重取**，不要给结论
- `available: false` —— 该端点没有页脚，只能靠 `pagination_complete` 判断，回答里要说明

页脚是最硬的证据，因为它不是"行数看起来对不对"这种感觉，而是后端用自己的口径独立算了一遍。
所以两种"页脚帮不上忙"的情况要单独识别，它们不能互相替代：

**没有页脚：`deliver-summary`。** 实测 `server_footers: []`。这时 `integrity.available` 是 `false`，
但完整性并不是无从判断——`kz-compute.mjs flow` 用收发汇总天然成立的恒等式顶替页脚：

```
期初 + 入库合计 − 出库合计 = 结存      （逐行成立）
```

`identity_check.matches` 为 `true` 说明这份数据自洽、没有丢行；为 `false` 时不要给结论。
有一点要老实承认：这条恒等式同时是 `flow` 解列含义的判据，所以它 `true` 主要说明求解一致。
真正独立的旁证是 `identity_check.cost_columns_agree`——金额列是另一套数字、没参与求解，
却满足同一条式子；以及 `column_mapping.solutions_satisfying_identity`，候选组合越少说明列含义越确定。

**有页脚但翻页不闭合：`bank-journal`、`payable-detail`。** 它们的 `data.total` 页脚是全量口径，
而行只是有界的第一页，所以 `integrity.all_match` 天然对不上，`pagination_complete` 永远是 `false`。
这不是 bug，也不该靠翻页去"修"（实测 `rows=1` 仍返回多行，第 2 页拿到的是重复数据）。
正确做法是把结果说成有界结果，并引用页脚数字回答总量、用行回答明细，两者分开表述。

### 后端混在明细里的伪行

有些报表会把"小计 / 期初余额 / 合计"这类汇总行塞进明细数组，行结构和真实明细一模一样。
把它们和明细行一起求和，等于把同一段区间算两遍——数字翻倍，但没有任何一处报错。

已知的一处：`profit-report` 会在顶层 `data[]` 末尾追加一行 `month="合计"` 的区间汇总行。
注册表用 `excludeRows` 声明了这个模式，`kz-fetch.mjs` 在落盘前剔除，并把剔了几行写进
`manifest.excluded_rows`；`kz-compute.mjs` 的 `source.excluded_rows` 会再报一次。

两个推论：**落盘文件里的行可以直接求和**，不需要你自己挑；但如果你绕过 `kz-fetch.mjs` 自己请求，
这一行要自己处理。引用行数时用剔除后的 `row_count`，别用原始响应的长度。

### 分组键丢行

`rank` 和 `flow` 的分组是另一处会静默少算的地方：**分组键为空的行无法归属**。
脚本不会把它们合成一个空键的桶（那会把几十个不同商品并成一个假的"第一名"），而是丢掉并报
`dropped_rows_warning`，写明丢了多少行、多少金额。

实测的典型案例：`sales-detail` 里第三方仓（`location="第三方仓"`）商品的 `skuId` 是 `null`——
2026-08 整月 2128 行中有 41 行、涉及 30 个商品、6824.00 元。只按 `--group skuId` 排名，
这 41 行整批消失，`totals` 与页脚差 6824.00。补一个兜底字段 `--group skuId,number` 就都回来了
（分组数 1177 → 1207，`integrity.all_match: true`）。

所以看到 `dropped_rows_warning` 的处理不是"在回答里加个说明"，而是**换分组键重算**。
它出现意味着排名本身少算了东西，排序位次可能已经错了。

### 筛选丢行：比分组更隐蔽，因为它不触发上面那个警告

`--where` 在分组**之前**执行。如果被筛的字段在某些行上是空的，那些行在分组开始前就已经不在了，
于是 `rows_without_group_key` 是 0、`dropped_rows_warning` 不响——数据少了一块，而输出一切正常。

实测案例：`--where secondCategoryName=轮胎` 统计本月轮胎。第三方仓的行二级分类为空（见口径陷阱四），
其中一条 `categoryName="轮胎"`、`number="255/40R20 101W SPORT RX6"`、500.00 元的真实轮胎销售
被静默滤掉，轮胎合计 15362.00 被报成 14862.00。问"最畅销的轮胎是哪款"时它排不进前列、影响不大，
问"本月轮胎卖了多少钱"就直接答错，而且没有任何提示。

所以 `local_filter` 有两个字段要读，方向相反：

- `matched_values`：往多了看。命中了哪些取值，用来发现误伤（搜"轮胎"命中"轮胎清洗剂"）。
- `blank_field_rows`：往少了看。有多少行因为被筛字段为空而被滤掉，其中
  `also_matched_in` 会告诉你**同一个关键词是不是在这些行的别的字段上命中了**。
  命中就说明筛错了字段：改筛那个字段重算，或者把两部分相加，并在回答里说明这些行分类为空。

只看 `matched_values` 是看不见少算的——它展示的是筛选后**留下来**的东西。

### 分片丢行：错在取数阶段，所有完整性检查都看不见

上面两种丢行都发生在计算阶段——行已经在文件里了，只是没被算进去。还有一种更糟的：
**行压根没进文件。**

它这样发生：某个端点的全量超了 2 MiB 预算，于是你按某个字段分片、循环取、合并。
如果这个字段在部分行上是空的，那些行不属于任何一个分片值，循环无论跑多少轮都碰不到它们。

实测案例（真实翻过车的一次）：`inv-balance` 全量 3.75 MiB 取不动，于是按 `brandId` 遍历品牌。
第三方仓的行 `brandName` 是空的（见口径陷阱四），169 行 / 56186.88 元整批取不到——
库存总额被报成 972123.77，真值是 1028233.90，少 5.46%；更难看的是"第三方仓库存 0.00 元"
这个结论与事实正好相反，而真正的滞销第一名恰好就在这批看不见的行里。

**为什么每一道网都没兜住**，值得逐条看清楚，因为这决定了你不能依赖什么：

| 检查 | 当时的状态 | 为什么没用 |
|---|---|---|
| 页脚核对 `footer_reconciliation` | 每个分片都 `all_match: true` | 页脚是按**筛选后**口径算的。它证明"这个分片没丢行"，证明不了"分片集合覆盖了全表" |
| `possibly_truncated` | `false` | 每个分片都远小于上限，确实没被截断 |
| `dropped_rows_warning` | 不响 | 分组键没缺失——缺的行不在文件里 |
| `local_filter.blank_field_rows` | 0 | 没用 `--where`，本地一行都没滤 |

所以这类缺口只能**在取数时**发现。`kz-fetch.mjs` 为此在注册表里声明了已知的分片缺口
（`shardGaps`），一旦你带着那个窄化参数取数，清单里就会出现 `shard_coverage_warning`，
写明缺的是哪批行、实测多少行多少钱、以及补齐用的那一条命令。

看到它时的处理：

- 只查单个品牌/单个值 → 忽略，你要的就是这一片
- 想拼全量 → **必须**按提示补齐（`inv-balance` 就是再加一次 `--param storageNo=S001`），合并后再算
- 报数之前给总额找个独立旁证：`day-report` 最新一天的 `store_fee`（实测 1029704.23 vs
  全量页脚 1028161.90，差 0.15%）。量级对得上说明没漏掉一整块

更一般的教训：**遇到"全量取不动，那就分片"的时候，先问一句"这个分片键在所有行上都有值吗"。**
用 `--preview` 看几行、或者先取一个分片看清单里的 `shard_coverage_warning`，都比事后被用户
指出总额少了 5% 便宜。空值不是边缘情况——第三方仓的行在这个后端里成体系地缺 `brandName`、
`skuId`、`secondCategoryName`，同一批行已经在三个不同的地方咬过人了。

### 数据新鲜度是逐端点的

`integrity` 校验的是"同一份响应内部自洽"。跨端点比对是另一回事，那里有一个额外的失败模式：
**两个报表可能停在不同的日期上。**

实测 2026-08-22 同一时刻查本月：日报 `sale_fee − dbck_fee = 189715.20`，
利润表 `销售.sale_fee = 178769.20`，差 10946.00（毛利差 2941.65）。差额恰好等于 2026-08-21
一整天的净销售额与毛利；把日报只算到 08-20，两边逐分相等。日报已经收到 08-21，利润表还没有。

同一时刻的月报 `sale_fee` 是 194581.20，与日报本月合计逐分相同——所以落后的是利润表，
经营报表的日/月视图是同步的。这也说明"哪个端点更新"不能靠猜，要靠下面这个减法定位。

同一天里 `--date yesterday` 的结果也变过：早些时候 `row_count: 0`，几小时后 `row_count: 1`。
数据是当天陆续落库的，所以"昨天有没有数据"不能背结论，每次都要读 `date_coverage`。

跨报表对不上时按这个顺序判断，别急着二选一：

1. 把较新的那张表按日期从新到旧逐日剔除，看差额是否**正好**等于被剔掉的那几天（写脚本减，不要目测）
2. 等于 → 新鲜度差异，两张表都没错。报较新的口径，并说明另一张截至哪天
3. 不等于 → 才是真的口径差异或完整性问题，这时不要给结论

把新鲜度差异当成"哪张表算错了"，会让你去质疑一个正确的数字；反过来，把真正的口径差异
当成新鲜度差异放过去，会让错误结论带着"已核对"的标签发出去。两个方向都靠上面这个减法区分。

### 无界断言：问题问的是"从来"，端点只给得出"这段时间"

上面几节都是"这份数据有没有丢行"。这一节是另一回事：**数据本身完整，但它覆盖的时间跨度
比问题小。** 用户说"从来没卖过""一直没动过""有史以来最高"时，判定域是账号的全部历史；
而销售明细/汇总类端点单次上限 7 天，`--split` 只是把用户给的区间切开，不会替你把区间变长。

这类错误的特征是**答案本身每个数字都对，只是回答的不是那个问题**——所以既不会有警告，
也无法靠核对页脚发现。三步处理：

1. **先找无界字段。** 有些字段天生记录"最近一次"而不是"这段时间内"，它们就是无界证据。
   库存余额的 `out_time`（最近出库时间）是典型：一笔销售必然是一次出库，所以
   "最近销售时间 ≤ out_time"，于是 **`out_time` 为空 ⟹ 从未出库 ⟹ 必然从未卖出**。
   这个推理不依赖任何时间窗口，是可以直接说出口的结论。
2. **说清误差方向。** 无界字段通常只给出**单边**结论。上面那条反过来不成立：`out_time`
   非空只说明出过库，而出库还包括调拨等非销售动作，所以"从未卖出"的真实名单比
   "`out_time` 为空"更大。实测差距不是零头：`out_time` 为空得 2286 款 / 220090.45 元，
   全历史零销售记录的真值是 2524 款 / 251898.59 元，漏掉 238 款 / 31808.14 元
   （占真值款数 9.43%、金额 12.63%）。给了下界就要说它是下界，别让用户以为是全部。
3. **先量一下历史有多长，再决定要不要扫完。** 不要想当然认为"全历史扫不动"。
   用 `month-report` 探起点（单次上限 12 个月，所以查 2–3 段就能定位第一个有销售的月份），
   实测这个账号从 2024-04 才有数据、2024-05 起才有销售——27 个月切成 126 个 7 天窗口，
   两个销售端点各扫一遍几分钟就完了。历史短的时候就该扫完，把"无法判定"变成真答案；
   真的太长再退回下界，并说明退到了哪一步。

配方见 `recipes.md` 的"从来没卖出过的商品"。

### 不允许的"补全"手段

为了让数字看起来完整而做以下任何一件事，都会把静默错误引入结论：

- 加大 `rows` 绕过字节上限
- 用短页经验规则自动续页
- 自动切换到 `*-cost` 端点（成本是敏感数据，需用户明确要求 + `--allow-cost`）
- 自动扩大用户给的日期范围

`--split` 不属于扩大范围：用户要的区间没有变，只是把它切成若干个各自满足 7 天/2 MiB 预算的窗口。
但每个窗口都必须成功，任一窗口报错就整体作废。

## 五、成功谓词与 fail closed

**HTTP 200 不等于查询成功。** 快准车服的成功谓词逐端点不同：

| 谓词 | 端点 |
|---|---|
| `status === 200` | `day-report`、`profit-report`、`sales-detail`、`sales-detail-cost`、`sales-summary-*`、`sales-order-list`、`sales-reconcile-detail`、`key-account-sales-detail`、`key-account-return-detail`、`inv-balance`、`deliver-summary`、`bank-journal`、`customer-balance`、`store-list`、`settle-account-list` |
| `success === true && status === "success"` | `month-report`、`sales-return-list`、`key-account-sales-list`、`key-account-return-list`、`receipt-list`、`payable-detail`、`category-tree`、`brand-list`、`contact-home`、`key-account-category`、`warehouse-list`、`employee-list`、`pay-method-list` |

注意 `day-report` 和 `month-report` 谓词不同——同一个报表的日/月视图，后端实现不一致。
这类差异正是不能用一个通用解析器的原因。

谓词不满足时脚本报 `UPSTREAM_QUERY_FAILED` 并读取后端 `msg`。你在解读时守住同样的纪律：
**空数组要能区分"确实没有业务发生"和"查询根本没成功"**。前者可以回答"这段时间没有销售记录"，
后者必须报告查询失败。

### 例外：空结果哨兵

大客户两个列表端点（`key-account-sales-list` / `key-account-return-list`）在**查询成功但没有单据**时，
返回的信封形态与成功时不同：`status === "-1"` + `msg === "没有数据"` + `data` 是长度 0 的数组。
成功谓词必然不满足，可它表达的恰恰是"没有业务"，不是"查询失败"。

脚本按四项**同时**成立才归一为空列表，并在清单里写 `empty_result_sentinel` 和
`pagination_complete: true`。为什么要卡这么死：放松任何一项，真正的查询失败就会伪装成
"这段时间没生意"；而不识别它，"这段时间没生意"就会被报成"查询失败，无法回答"。
两个方向的错都会直接改变你给用户的结论。

看到这个标记时，说"这段时间没有相关业务发生"。不要说"金额 0 元"（那听起来像有单据但金额为零），
也不要说查询出错。

网关错误信封是 `{"error": {"code", "message", "requestId"}}` + 非 2xx 状态码；
业务响应从不套这层信封，所以两者可以明确区分。错误码含义见 `SKILL.md` 的"出错时怎么办"。

## 六、只读边界

注册表里没有任何写接口，但边界要说清楚：

- 不得把只读路径改造成保存、编辑、删除、审核、导入、导出、调拨、开单、组装拆包、报价维护。
- 网关在 Agent 模式下已禁止 `/passport/login/*` 和 `/api/agent-credentials*`：会话自动维护，
  你既不需要也不允许自己登录或管理凭证。
- 网关对失效会话会自动重登录并**重放原请求最多一次**。对只读查询这没有副作用；
  这也是另一个不能碰写接口的理由——重放会让一次写操作执行两次。
- 用户要求做写操作时明确拒绝并说明原因，不要"帮忙"找变通路径。
